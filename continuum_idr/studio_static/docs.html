CONTINUUM IDR RESEARCH SDK

Vehicle Dead Reckoning Navigation Fallback

Continuum is an autonomous dead-reckoning engine designed for Smart India Hackathon SIH168. It fuses smartphone inertial sensors (accelerometers, gyroscopes) with learned longitudinal speed estimation, an Extended Kalman Filter (EKF), zero-velocity updates (ZUPT), and kinematic constraints to maintain position continuity when GNSS is lost.

Research Prototype & Evidence Boundary

This system runs real-time Python and Kotlin algorithmic pipelines on recorded vehicle trials (IO-VNBD dataset). It is NOT live smartphone sensing and NOT certified aviation/automotive navigation. Current held-out benchmark drift misses the <10% target without external wheel odometry or road map-matching. We report all evaluation metrics transparently.

01 Causal Inference Consumes time-ordered IMU samples without future knowledge or non-causal lookahead.
02 Zero-Dependency Mobile Core Exported portable JSON decision trees evaluate in pure Kotlin on Android in <150 µs.
03 Transparent State Exposes tracking mode, covariance uncertainty radius, GPS decision gating, and health flags.
GET STARTED

Run Your First Engine Session

Install the package in editable mode, load the trained P0 model bundle, configure the engine, and stream sensor events in timestamp order.

1Install Package & DependenciesRun in your Python 3.10+ virtual environment:
pip install -e .
python -m pytest tests/
2Initialize IDREngineMatch IMU sampling frequency to model specification (10 Hz):
from continuum_idr import IDREngine, EngineConfig, MotionModelBundle

# Load trained gradient boosting speed model
model = MotionModelBundle.load("models/motion_p0")
config = EngineConfig(imu_rate_hz=10.0, gnss_timeout_s=12.0)
engine = IDREngine(config, model)
3Stream Sensor EventsDeliver GNSS fixes and IMU samples monotonically:
from continuum_idr import GNSSFix, IMUSample

# Seed initial position with accepted GNSS
engine.on_gnss(GNSSFix(
    timestamp_s=100.0, latitude_deg=52.4001, longitude_deg=-1.5002,
    speed_mps=12.5, course_deg=92.0, horizontal_accuracy_m=3.5
))

# Propagate dead-reckoning state at high frequency
state = engine.on_imu(IMUSample(
    timestamp_s=100.1, accel_mps2=(0.12, 0.05, 9.81),
    gyro_radps=(0.001, -0.015, 0.002),
    gravity_mps2=(0.0, 0.0, 9.81)
))
print(f"Mode: {state.tracking_mode.value}, Speed: {state.speed_mps * 3.6:.1f} km/h, Uncertainty: ±{state.horizontal_uncertainty_m:.1f}m")
CORE CONCEPTS

Tracking Modes & Lifecycle

Continuum maintains a single continuous estimator throughout the entire journey. Incoming IMU samples propagate dead-reckoning motion. Accepted GNSS fixes correct drift. When fixes cease, uncertainty naturally grows.

Tracking Mode Operational Meaning Client UI Responsibility
UNINITIALIZED Awaiting initial high-confidence absolute GNSS fix Do not render a fabricated vehicle position
GNSS_AIDED GPS fixes fused with inertial propagation Display normal green positioning state
DEAD_RECKONING GPS lost or withheld; EKF running on IMU + ML speed Show amber fallback badge and display uncertainty ring
RECOVERING GPS re-acquired; validating fixes with innovation gating Show blue status; avoid instant discontinuous jump
LOCAL EXPERIMENT HTTP API

Runtime HTTP Endpoints

Studio and the mobile driver view connect to an interactive local HTTP API defined in docs/RUNTIME_API.md. This API runs IDREngine directly on raw recorded IO-VNBD sensor measurements.

HTTP Request Endpoint Description
GET /api/runtime Lazily initializes SDK session, advances due samples based on elapsed wall time, and returns complete snapshot.
POST /api/runtime/control Applies a runtime control action (play, pause, step, gnss, rate, restart) and returns the updated snapshot.
GET /api/runtime/export Advances due samples and downloads the current session snapshot as a JSON file.
GET /api/summary Serves historical benchmark results (34 outages). Unrelated to manual experiment controls.
GET /api/health Basic process status. Note: status: ready alone does not certify runtime initialization; /api/runtime is authoritative.
LOCAL EXPERIMENT HTTP API

Control Contract & Payloads

Send a JSON body with action and optional value to POST /api/runtime/control:

Action Value Runtime Effect
play omitted Resumes continuous playback. Completed sessions require restart.
pause omitted Pauses processing after catching up a bounded batch.
restart omitted Creates a fresh engine instance, resets warm-up, pauses, restores GPS to enabled, 1x rate, and assigns a new session ID.
gnss false / true Deliver or withhold subsequent newly recorded GPS fixes from the engine.
step Integer 1–100 Processes the next N recorded samples while paused; clamps at end of recording.
rate 0.5, 1.0, 2.0, 4.0 Source-time playback multiplier relative to real wall clock time.

LOCAL EXPERIMENT HTTP API

Timing & GPS Semantics

GET and control requests advance at most 100 samples toward the recorded timestamp corresponding to elapsed monotonic wall time and playback rate. There is no autonomous background worker when no HTTP requests arrive; polling drives bounded processing.

  • GPS Withholding is Manual: GPS starts enabled. Toggling to withheld blocks on_gnss() calls while on_imu() continues. It does not rewrite past history or instantly change tracking mode until timeout (12s).
  • Restoring GPS: Admits future newly recorded fixes; it does not backfill withheld fixes. The engine's innovation gate may reject degraded fixes upon re-entry.
  • Serial Polling: Clients must poll serially (200–300 ms), suspending polls while a control request is in flight to prevent stale race conditions.

Held-Out Evaluation Results

Interpreting the Results

Continuum IDR outperforms frozen GPS by +28.7% overall and +48.0% on short 50m outages. However, consumer MEMS gyroscopes accumulate unconstrained lateral drift on curves over extended outages without road map matching or CAN wheel speed odometry.

EVIDENCE & BOUNDARIES

Known Limitations

  • Phone GPS Update Rate: In IO-VNBD recordings, raw smartphone GPS updates at ~0.1 Hz (~9–10s intervals), requiring time-based filtering.
  • Consumer Gyroscope Drift: MEMS gyros experience thermal drift that degrades heading orientation over long durations without map constraints.
  • Mounted Phone Requirement: Evaluated assuming a windshield/dashboard mount. Handheld shaking introduces high vertical vibration noise.
  • Pure Software Fallback: Without access to vehicle CAN wheel-speed sensors, high-accuracy multi-kilometer dead reckoning remains challenging.
